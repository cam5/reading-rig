## Summary

Two unrelated streams of work landed in this range.

1. **Web: an experimental paged reading mode.** `/read/:workId?mode=paged`
   shows the book one fixed page at a time, with prev/next buttons and
   arrow keys, in place of the scrolling column. It is URL-gated with no
   UI toggle. Page breaks come from CSS multi-column layout, and all
   "what is on this page" answers come from measuring the browser's real
   layout. The mechanism lives in a new standalone package,
   `lib/paged-columns`.
2. **Native client: real typeface, real selection, real app target.** The
   Swift client now bundles the Fraunces reading face, lets a macOS reader
   drag-select a range and highlight exactly that, and has an iOS app
   target generated by XcodeGen. A fourth commit renames the font folder
   to get past an Xcode codesign failure.

What actually changed for someone who never types `?mode=paged`:

- Scroll-mode paragraphs now hyphenate (`hyphens: auto`). This is the one
  deliberate change to the default reader.
- The empty-work message moved to a different place in the layout.
- `read.tsx` runs the paged-mode hooks on every render in both modes. The
  cost of that is already addressed by open PR #214.
- Scroll-mode bookmark, section and progress logic is unchanged: it was
  moved into a shared function, verbatim.

One cross-commit interaction is worth knowing before reading the iOS
sections: #207 bundles Fraunces, and #210's folder rename leaves the font
lookup pointing at the wrong level of the bundle, so on a clean build the
reading font silently falls back to the system font. Open PR #211 fixes
that. At `98ab6df` the fix is not in.

### `e3db0c8` Bundle the real Fraunces typeface (#207)

9 files, +237 / −81.

**Intent.** Make the native client's reading text use the same typeface
the web uses, at the same pinned variable-font point, and fix two layout
bugs that only became visible once it did.

**Behaviour changes (native client).**

- Reading text renders in Fraunces rather than the system serif.
  `RigTheme.readingFont` (`ios/Sources/ReadingRigUI/RigTheme.swift:27`)
  switches from `Font.system(size: 17.5, design: .serif)` to
  `FrauncesFont.regular(size: 17.5)`. `RigChatView.swift:73` also reads
  `RigTheme.readingFont`, so the Rig chat view changes face too. The
  commit message does not mention that.
- Blockquotes use Fraunces' own italic drawing
  (`RigTheme.readingFontItalic`, `RigTheme.swift:31`) where before SwiftUI
  synthesised an oblique from the roman.
- Paragraphs are now separated by 9pt, the same value as the gap between
  wrapped lines, where before the stack spacing was 0. The value is named
  once as `RigTheme.readingLineSpacing` (`RigTheme.swift:45`).
- The first-line indent is three non-breaking spaces (U+00A0), so layout
  no longer trims it at wrap boundaries.

**Contracts and invariants introduced.**

- The font is registered per process at first use, through a lazy static
  in `FrauncesFont` (`FrauncesFont.swift:30`). Nothing is installed
  system-wide.
- The PostScript names are `Fraunces-9ptBlack` and
  `Fraunces-9ptBlackItalic` (`FrauncesFont.swift:25`). They describe the
  source font's nearest named instance, and the real weight is 340. A
  mismatch between these strings and the generated TTFs fails silently:
  `Font.custom` falls back to the system font.
- The same silent fallback applies when the bundle lookup misses
  (`FrauncesFont.swift:32` uses `guard ... else { continue }`). This is
  the failure mode #211 is about.
- Coverage is the `latin` unicode range only. The web ships `latin` and
  `latin-ext`. Characters in Latin Extended-A fall back to a system font
  on the native client. The script's header documents this as deliberate.
- The generated TTFs are committed binaries. `instanceFrauncesForIOS.ts`
  is in no `package.json` script, whereas the web's `instanceFraunces.ts`
  runs on every `predev`, `prebuild` and storybook start. If
  `VARIATION_AXES` changes, the web follows automatically and the native
  client does not.

**Refactor only.** `scripts/instanceFraunces.ts` lost its constants to
`scripts/lib/frauncesInstancing.ts` (`SOURCE_DIR`, `VARIATION_AXES`,
`LATIN_RANGES`, `LATIN_EXT_RANGES`, `rangesToText`). I compared the moved
values line by line: identical, with `SOURCE_DIR` adjusted by one `../`
for the new directory depth. The web script still requests `woff2` for
both ranges (`scripts/instanceFraunces.ts:37`), so web font output is
unchanged. The reason for the extraction is real: both scripts call
`main()` at import time, so importing one from the other would run it.

**Risk.** Low for the web. For the native client the risk is the quiet
failure mode above.

**Tests.** None added. The only Swift test file is still
`ios/Tests/ReadingRigKitTests/BearerAuthMiddlewareTests.swift`.

### `83c7d51` Drag-to-select highlighting on macOS (#208)

4 files, +332 / −92.

**Intent.** Let a macOS reader highlight an arbitrary range. SwiftUI
`Text` cannot report a selected range, so paragraphs are rendered through
a wrapped `NSTextView`.

**Behaviour changes.**

- macOS: each paragraph is a selectable, non-editable `NSTextView`
  (`SelectableParagraphText.swift:19`). With a selection active, the
  context menu gains "Highlight Selection" above "Highlight Paragraph"
  (`WorkReadView.swift:213`).
- macOS: inline `<em>` and `<strong>` are no longer rendered. The whole
  paragraph is forced to one font after bridging

  documents in `ios/README.md`.
- iOS: no behaviour change. The `#else` branch is the previous `Text`.

**Contracts and invariants.**

- **Offset coordinate space.** The server's highlight offsets are UTF-16
  offsets into `paragraph.text`. The text view's string is that text with
  a 3-character indent prepended for every paragraph that is not first in
  its section. `ParagraphRow` owns the translation in both directions:
  it subtracts `indentLength` from a selection before posting
  (`WorkReadView.swift:251`) and adds it when painting existing spans
  (`WorkReadView.swift:300`). `indentLength` (`WorkReadView.swift:200`)
  and the indent string (`WorkReadView.swift:331`) must stay in sync; a
  comment says so and nothing enforces it.
- I checked that the unhighlighted path does not break this. That path
  builds its string from `paragraph.html` via `InlineHTML`, and
  `sanitizeHtml.ts:159` derives `text` as the `textContent` of the same
  node `html` comes from, so the two strings agree.
- On macOS, visual attributes no longer come from the `AttributedString`.
  Font, colour, line spacing and highlight tint are reapplied natively,
  because the bridge to `NSAttributedString` dropped them. The highlight
  tint is therefore defined twice, at `WorkReadView.swift:303` and
  `WorkReadView.swift:359`, with the same value today.
- `FrauncesFont`'s PostScript name constants went from `private` to
  internal, and `ensureRegistered()` is new. Anything building an
  `NSFont` by name must call it first.
- Selection is per paragraph. Each row holds its own `selectedRange`, so
  a highlight cannot span paragraphs.

**Refactor only.** `paragraphView` became `rowView` plus a private
`ParagraphRow` view, so each row can hold state. `highlightWholeParagraph`,
`postNote` and `load` moved within the file unchanged. `attributedText`
and `highlightedText` moved into `ParagraphRow` and read `paragraph` from
`self`.

**Risk.** Medium, and confined to the macOS dev shell. The commit message
itself says the drag gesture and right-click menu could not be confirmed

**Tests.** None.

### `1727b6f` Rename the font folder off "Resources" (#210)

5 files, +14 / −3.

**Intent.** Xcode's codesign rejects a resource bundle that contains a
directory literally named `Resources`. Rename it to `Fonts`.

**What it means.** The textual change is a rename in three places:
`Package.swift:54`, the script's output directory
(`scripts/instanceFrauncesForIOS.ts:37`), and a doc comment. The TTFs are
byte-identical renames.

The semantic change is larger than the diff. The commit message says the
lookup code "was already keyed by resource name, not folder name, so
nothing else needed to change". That turned out to be wrong:
`.copy("Fonts")` keeps `Fonts` as a nested directory, and
`Bundle.module.url(forResource:withExtension:)`
(`FrauncesFont.swift:32`) searches only the bundle's top level. The old
name worked because a top-level `Resources` directory is an implicit
search location. So this commit fixes the build and, on a clean build,
undoes #207's visible effect. It went unnoticed because a stale
`Resources/` folder survived in `ios/.build/`.

All of that is from open PR #211's description, which adds
`subdirectory: "Fonts"` to the lookup. I confirmed only that the lookup
at `98ab6df` has no `subdirectory:` argument. This is a known follow-up
and is not raised again below.

**Risk.** As above: correct build, silently wrong typeface until #211
merges.

**Tests.** None. A font-name or font-lookup assertion would have caught
this, and none exists.

### `98ab6df` Experimental paged reading mode (#212)

14 files, +1730 / −160.

**Intent.** A second reading mode that presents fixed pages. An earlier
attempt computed page height from a sampled line height and clipped with
`translateY`, and it cut through lines in real Chrome. This one delegates
page breaking to the browser.

#### New public surface: `lib/paged-columns`

Exports (`lib/paged-columns/index.ts`):

| Export                                                  | Role                                                                                          |
| ------------------------------------------------------- | --------------------------------------------------------------------------------------------- |
| `estimateMountWindow`, `growMountWindow`, `MountWindow` | Pure. Decide how many items to mount around an anchor, from caller-supplied size guesses.     |
| `columnIndexForOffset`                                  | Pure. Turn a measured horizontal offset into a column number.                                 |
| `usePagedColumns`, `PagedColumnsItem`, `VisibleItem`    | The hook: owns frame and columns refs and styles, measures fragments, and exposes navigation. |
| `PagedNavControls`                                      | Prev/next buttons, plus a document-level ArrowLeft/ArrowRight listener.                       |

The package knows nothing about books. Its item is
`{ id, estimatedSizePx }`.

Its design rests on three invariants:

1. **Estimates size the mount window and nothing else.** Where a page
   boundary falls is always read from `getClientRects()`
   (`usePagedColumns.ts:156`, `usePagedColumns.ts:286`). A bad estimate
   costs a grow-and-retry round, bounded by `MAX_GROW_ATTEMPTS = 8`
   (`usePagedColumns.ts:154`).
2. **Page identity is an anchor item id plus a fragment index.** There is
   no page number anywhere. On a width or height change the fragment
   index resets to 0 (`usePagedColumns.ts:279`), so a resize lands on the
   start of the same paragraph.
3. **Column positions are uniform.** Every column is
   `columnWidthPx + columnGapPx` apart, so dividing a measured offset by
   that step is exact. Offsets are taken relative to the columns
   element's own rect, which cancels the `translateX` that selects the
   page.

Two navigation contracts follow from measuring real layout:

- A forward turn commits only once the target column is confirmed full,
  meaning a fragment exists one column beyond it or the mount window has
  reached the end of the list (`usePagedColumns.ts:350`). Otherwise the
  hook grows the window and retries on the next layout pass.
- `canGoNext === true` means "not yet known to be false"
  (`usePagedColumns.ts:584`). `goToNextPage()` returning `true` may mean
  a retry was queued.

A new `items` array identity rebuilds the id-to-index map during render
(`usePagedColumns.ts:221`). The doc comment on `items` says it also
resets the mount window; the code does not do that, and `read.tsx`
instead calls `goToItem` itself after prepending rows.

#### Changes to the read route

- **Gate.** `pagedMode` is `searchParams.get("mode") === "paged"`
  (`app/routes/read.tsx:455`). It is client-side only; the loader and
  action are untouched and both modes consume the same loader data.
- **Both strategies always run.** `useVirtualizedRows` and
  `usePagedColumns` are both called every render
  (`read.tsx:567`, `read.tsx:592`), as are both bookmark trackers
  (`read.tsx:712`, `read.tsx:722`). `startIndex`, `endIndex` and
  `registerRowRef` are picked from the active one
  (`read.tsx:610`), so everything downstream is mode-agnostic. This is
  the code path that touches scroll mode with the feature off; see
  PR #214.
- **Row rendering is shared.** `renderRow` (`read.tsx:979`) is the old
  inline `.map` body, extracted. The only additions are
  `justify={!pagedMode}` and `hyphenate={!pagedMode}`.
- **Section jumps and "load previous" have paged twins.**
  `paged.goToItem` and `paged.captureAnchorItemId` stand in for
  `scrollToRow` and `captureAnchor`, with a paged pending-id ref settled
  in the same layout effect (`read.tsx:816`).
- **"Load previous section" in paged mode** is shown only when there is
  no previous page within what is loaded (`read.tsx:1039`), and it sits
  inside the column flow, so it takes space from the first page.

#### Bookmark tracking: one resolver, two candidate sources

`resolveBookmarkFromCandidates`
(`app/components/useBookmarkTracker.ts:117`) is the old body of
`settle()`, extracted. Given a list of candidates and a viewport height
it does three things: reports the on-screen section and rewrites the URL,
submits a bookmark when the reader is further than known, and returns
progress, time left and the visible ordinal range.

Scroll mode is a pure refactor here. I compared the extracted function
with the removed lines: same statements in the same order, with
`current.clientHeight` passed as `viewportHeightPx` and the same ref
passed as `knownGlobalOrdinalRef`. Candidate gathering, the 400ms
debounce and the mount-time `settle()` are untouched.

Paged mode (`usePagedReadingBookmarkTracker.ts`) feeds the same resolver
differently, and the meanings shift:

| Question        | Scroll mode                                              | Paged mode                                                      |
| --------------- | -------------------------------------------------------- | --------------------------------------------------------------- |
| Candidates      | Every mounted `[data-paragraph-id]`, from a DOM scan     | Only fragments measured on the current page (`visibleItems`)    |
| Trigger         | Scroll settle, debounced 400ms, plus once on mount       | `pageKey` change, no debounce                                   |
| Viewport height | The column's `clientHeight`                              | `Infinity`, since candidates are pre-filtered                   |
| Bookmark        | Furthest paragraph whose top is above the 40px read line | The paragraph at the top of the page (the only tops under 40px) |
| Marginalia span | The whole mounted window, overscan included              | Exactly the paragraphs on the page                              |

Dividers are in `visibleItems` and are dropped by the id lookup, as in
scroll mode. The bookmark stays monotonic in both modes.

#### Shared components touched

- `ReadingParagraph.module.css:32` adds `hyphens: auto` to every reading

  then turned off there by the last commit in the PR because it corrupted

  one mode that does not get it.
- `ReadingParagraph.tsx:137` adds `justify` and `hyphenate` props, both
  defaulting to `true`. The comment on `justify` says it was disabled in
  paged mode as a precaution and was not shown to be at fault.
- `SelectionHighlighter.tsx:368` adds `min-w-0` to its flex wrapper in
  both modes. In scroll mode the child already had the overflow carve-out,
  so this should be inert there **(by reading)**.
- `ChapterSectionDivider.tsx:56` sets `break-inside` and `break-after` to
  `avoid-column`. These do nothing outside a fragmentation context, so
  scroll mode is unaffected. `break-after` is honoured in multi-column
  layout by Chromium only.
- `vitest.config.ts:48` adds `lib/**/*.test.ts` to the test include.
  `lib/` is already covered by `tsc` (the `tsconfig.json` include is
  `**/*`) and by Prettier.

**Risk.** Medium inside `?mode=paged`, which is explicitly experimental.
Low but non-zero outside it: hyphenation, the moved empty-state message,

**Tests.** `lib/paged-columns/columnMath.test.ts` adds 12 cases covering

## Observations and questions for the author

These are observations from reading. No code was changed, none of them
was reproduced at runtime, and no issues were opened.

**Already tracked, listed so they are not raised twice**

- Paged-mode hooks run in scroll mode: open PR #214.
- Fraunces not found after the folder rename: open PR #211.

**New**

1. **The paged tracker may resolve the previous page (by reading).**
   `usePagedReadingBookmarkTracker`'s effect depends on `pageKey` only
   and reads `visibleItems` through a ref assigned during render
   (`usePagedReadingBookmarkTracker.ts:85`,
   `usePagedReadingBookmarkTracker.ts:139`). `pageKey` is derived from
   the anchor state, which changes in the render that follows a page
   turn. `visibleItems` comes from `measurement`, which is set by the
   layout effect of that same render and so only arrives one render
   later (`usePagedColumns.ts:357`). React flushes the passive effect of
   the first render before that second render, so the effect would see
   the old page's items, and nothing re-runs it afterwards because
   `pageKey` has not changed again. If that is right, section, bookmark
   and marginalia scope trail by one page, the first page resolves
   against an empty list, and the last page read in a session is never
   bookmarked. The doc comment on `pageKey` ("changes exactly when
   `visibleItems` might have") describes the intent and not the timing.
   Worth one check in a browser: turn a page and compare the `?section=`
   value and the marginalia with what is on screen.
2. **A page turn drops `mode=paged` from the URL.** The resolver rewrites
   the URL to `/read/${workId}?section=...`
   (`useBookmarkTracker.ts:142`), with no other params. The mode
   survives in-session because `replaceState` does not notify the
   router, and a reload or a copied link opens scroll mode.
3. **Arrow-key paging ignores modifiers.** `PagedNavControls.tsx:44`
   handles any ArrowLeft or ArrowRight outside an editable target and
   calls `preventDefault`. That includes Cmd+Left (browser back on
   macOS), Alt+Left, and Shift+Arrow used to extend a text selection
   before highlighting.
4. **The empty-work message moved in scroll mode.** "This work has no
   ingested text yet." used to render inside the padded reading column.
   It is now a direct child of `SelectionHighlighter`'s flex row, after
   the column (`read.tsx:1233`), so it will appear as a narrow item to
   the right of an empty column **(by reading)**.
5. **Hyphenation ended up scroll-only.** Is that the intended end state,
   given that it was introduced for paged mode? It is the one user-facing
   change to the default reader in this range and the PR title does not
   mention it.
6. **`lang="en"` on the columns element** (`read.tsx:1184`) looks like a
   leftover from when hyphenation was active in paged mode. It is
   harmless, since the document is already `lang="en"`.
7. **`items` doc comment versus code.** The comment at
   `usePagedColumns.ts:48` says a new array identity resets the mount
   window. Only the id map is rebuilt.
8. **macOS: a new highlight may not repaint (by reading).**
   `SelectableParagraphText.updateNSView` replaces the text storage only
   when the plain string differs (`SelectableParagraphText.swift:42`).
   Adding a highlight changes attributes and leaves the string the same,
   so a row that stays mounted across the reload would keep its old
   attributes. The commit message says a freshly created highlight was
   seen rendering correctly, so the row may be getting recreated; worth
   confirming which.
9. **macOS: a selection inside the indent.** `adjusted`
   (`WorkReadView.swift:251`) clamps to zero, so selecting only the
   leading indent posts a zero-length span.
10. **Native fonts can drift from the web.** Nothing regenerates or
    checks the committed TTFs when `VARIATION_AXES` or the source package
    version changes.
11. **`AppRootView` exists twice**, in `ios/App/ReadingRigApp.swift:22`
