# Performance profile — 2026-10-22

The first server-side profile of the shared loader fetches, alongside a local
run of the existing Lighthouse budget. **Measurement only.** Nothing here was
optimized; the hotspots at the end are proposed follow-ups.

**No N+1s.** The two rows above the 10-statement flag were checked against a
query trace. Both are fixed fan-out:

- **fetchReadPageData's 14:** the access check, Work, chapters, and sections.
  Then the structural paragraphs, plus Prisma's relation loads for
  `section`/`chapter`. The section load is chunked into 3 `IN (...)` queries
  for 2049 ids. Then the 4 content-window queries and the reading position.
- **searchMentionCandidates's 18:** 4 top-level queries, then the nested
  `include` levels issued once per side.

Neither count grows with the result size.

### CPU profile: built server, `/read/<heaviest work>` × 106

`node --cpu-prof` on `react-router-serve ./build/server/index.js`, with curl
in a loop and no browser. A warm request takes ~22ms end to end and returns
559KB of uncompressed HTML. Self time across all requests:

- **~800ms, ~7.5ms/request:** react-router's turbo-stream serialization of
  loader data into the document (`flattenValue`, `stringify`,
  `StreamTransfer`, `flatten`).
- **~520ms, ~5ms/request:** SQLite I/O and Prisma's runtime (`performIO`,
  `prepare`, `@prisma/client` internals).
- **~165ms:** GC.

Serializing what the loader returns costs more than querying it.

## Hotspots, ranked

1. **The cover image is 74% of the home page's bytes.** One unresized cover,
   `/cover/<workId>`, transfers 380KB. That puts `/` at 514.5KB of its 550KB
   total budget. A second book with a cover would fail the check, and no
   code regression would have caused it.
   _Follow-up:_ serve a thumbnail-sized variant to the shelf, generated at
   ingest or with a width parameter on `/cover/*`. Keep the full image only
   where it's shown large. Consider `loading="lazy"` below the fold.

2. **`structuralParagraphs` is 68% of the read loader's payload, and
   serializing it is the biggest server CPU cost.** Each of the 2049 rows
   nests `section: { id, ordinal, chapter: { id, ordinal } }`. Those ids are
   long strings that embed the work id
   (`jane-austen/pride-and-prejudice@377c8b796227::c1::s1`), so each row
   carries the work id three times. Gzip hides most of this on the wire, but
   the server still pays ~7.5ms/request in turbo-stream encoding, and the
   client still parses it.
   _Follow-up:_ send section/chapter references as indices into the `work`
   outline the payload already includes, or send the structural tier as
   columnar arrays. That should cut the 502KB by well over half.

3. **The content window ships ~2.2× its byte budget.** The initial window
   targets `DEFAULT_CONTENT_BYTE_BUDGET` (100KB) but serializes to 220KB.
   `estimateBytes(wordCount)` sizes for the prose alone. Each row actually
   carries both `html` and `text` (deriveHighlights needs `text`), plus every
   scalar column.
   _Follow-up:_ either recalibrate `estimateBytes` against the real row
   shape, or `select` only the columns the reader uses. Then the budget
   means what it says.

4. **`searchMentionCandidates` runs on every keystroke and scans the whole
   work.** p50 is 3.3ms with 18 statements. Its `text: { contains }` /
   `body: { contains }` filters compile to `LIKE '%q%'`, which is an
   unindexed full scan of `Paragraph`. The two paragraph queries take
   ~5–8ms each on a cold trace. Cost grows linearly with the text on the
   shelf. Each side also loads `html` + `text` for up to 8 paragraphs that
   the merge may discard. With no entries, it still issues
   `Work.id IN (NULL)` lookups.
   _Follow-up:_ an SQLite FTS5 index over `Paragraph.text` / `Entry.body`,
   and leaner includes on the candidate queries.

5. **The reading route's script bytes are the closest deterministic budget to
   its ceiling.** They grew from 172KB to 185.7KB (88% of 210KB);
   `read-*.js` alone is 78KB.
   _Follow-up:_ run a bundle analysis of the read chunk before #64's
   decomposition, so that work has a baseline to compare against.

6. **The annotation paths are unmeasured.** The seeded database has no
   highlights or entries. `fetchContentWindow`'s highlight over-fetch,
   `fetchCommonplaceShelf` and note mentions only show their empty-case cost
   here. The profiler stays read-only by design, so it can't create them.
   _Follow-up:_ an annotated fixture database, or a seed step behind a flag,
   so the next profile covers a reader with a few hundred notes.

Also worth doing: update `lighthouserc.cjs`'s header comment and its "observed
medians" table to today's numbers. The time ceilings (5s / 7s) are now 2–2.5×
the observed medians and could be tightened once CI runner numbers exist.
