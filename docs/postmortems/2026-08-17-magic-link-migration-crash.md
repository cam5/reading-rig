## Summary

Production went down (502s, crash-looping) when prod first ran the
`20260811013131_add_magic_link_auth` migration against its real, populated
`User` table, shortly after PRs #186 and #187 merged (PR #188). The
migration added `User.email` as `NOT NULL UNIQUE` with no backfill for
pre-existing rows. PR #188 fixed the migration in place — backfilling a
placeholder email for legacy users and making the script idempotent — so
prod's retry could resume from the half-applied state.

## Impact

- Prod: 502s, service crash-looping (PR #188: "confirmed 502s").
- Pre-magic-link (legacy) accounts were given a synthesized
  `legacy-<id>@reading-rig.invalid` email by the fix, so they can't sign in
  via magic link. PR #188 records this as an accepted consequence of the
  migration replacing anonymous auth wholesale, not something the fix
  set out to solve.
- No data was deleted by the fix (the backfill exists so the constraint
  can be satisfied "without deleting anyone's data").

## Root cause

From PR #188:

- `20260811013131_add_magic_link_auth` added `User.email` as
  `NOT NULL UNIQUE` with no backfill. Pre-magic-link accounts had no email
  column at all.
- It passed everywhere — CI, PR environments, staging-qa — because every
  one of those resets to an empty database before migrating. Prod's
  populated `User` table was the first place it ran against real rows.
  This is the same failure class MIGRATIONS.md already documents from the
  `wordCount` incident ("empty-elsewhere is not evidence of empty-in-prod").
- Compounding it: Prisma's SQLite migration runner does **not** roll the
  whole script back on a mid-script failure (reproduced locally). The
  failed run left `MagicLinkToken` created and an empty, orphaned
  `new_User` table behind, with the real `User` table untouched — confirmed
  identical in prod's crash logs.

## Resolution and recovery

- PR #188 rewrote the migration to backfill a synthesized
  `legacy-<id>@reading-rig.invalid` email for every existing `User` row,
  and made it idempotent (`CREATE TABLE IF NOT EXISTS`,
  `DROP TABLE IF EXISTS`) so a corrected retry resumes cleanly from the
  half-applied state rather than needing manual table surgery first.
- Verified locally against a `dev.db` stuck in the same failed state:
  `prisma migrate resolve --rolled-back` then `prisma migrate deploy`
  applied cleanly and backfilled the legacy row; `migrate diff` showed no
  drift.
- PR #188's remaining (unchecked) post-merge step: resolve prod's stuck
  failed-migration bookkeeping and redeploy, then verify `/healthz`
  returns 200.
