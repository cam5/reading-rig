# ios/

The reading-rig iOS client, nested in this repo rather than a separate one
so an agent editing it can read `app/domain` and `openapi/` directly. It
does not participate in the Node/Railway build — nothing in `package.json`
or `railway.toml` looks inside this directory.

**Current state: a Swift package, not yet a real app.** There is no
Xcode project, no bundle id, no app icon — nothing installable on a
device or in a simulator. Everything here builds and runs today via plain
`swift build` / `swift run`, which needs only the Command Line Tools for
the library targets, and a real Xcode install (not just CLT) for
`swift test` (XCTest.framework ships inside Xcode.app) and eventually for
signing/device deployment. Turning this into a real app is a separate,
not-yet-done step — see "Not built yet" below.

## Layout

- **`ReadingRigKit`** — networking and models only, no SwiftUI import.
  - `Sources/ReadingRigKit/openapi.json` is a **symlink** to
    `../../../openapi/api-v1.json`. The `swift-openapi-generator` SwiftPM
    build plugin (declared in `Package.swift`) reads it at compile time and
    generates `Types.swift`/`Client.swift`/`Server.swift` into `.build/`
    (gitignored, not committed — there is no other source of truth for
    them). This means the generated client updates itself automatically
    whenever `openapi/api-v1.json` changes; no manual codegen step to
    remember.
  - `ReadingRigClient.swift` — `BearerAuthMiddleware` (attaches
    `Authorization: Bearer`) and a thin factory over the generated `Client`.
  - `AuthSession.swift` — Keychain-backed `(baseURL, token)` persistence,
    `@Observable`, hands out a configured `Client`.
  - `ReadActions.swift` — hand-written convenience wrappers
    (`postHighlight`/`postNote`/`postBookmark`) over the generated
    `postReadAction` call, plus `HighlightSpanInput` (the wire shape
    `spansJsonSchema` on the server expects: a JSON-encoded string field).
  - `ModelAliases.swift` — short names for the deeply-nested generated
    response types (`ShelfWork`, `ReadableWork`, `ContentParagraph`).
- **`ReadingRigUI`** — SwiftUI screens, depends only on `ReadingRigKit`.
  - `RigTheme.swift` — colors hand-copied from `app/styles/organic.css`'s
    `--color-*` custom properties. **Not auto-synced** — there is no
    shared design-token source between the web app and this client yet, so
    if the web palette changes, this needs updating by hand. Single
    palette only (no dark mode), matching organic.css having none either.
  - `ShelfListView.swift` — `GET /api/v1/home`.
  - `WorkReadView.swift` — `GET /api/v1/read/:workId`, plus creating
    highlights/notes via `POST /api/v1/read/:workId`.
  - `SignInView.swift` — paste-a-token screen (see Auth below).
  - `NoteComposerView.swift` — the note-body compose sheet.
- **`ReadingRigDevApp`** — a `swift run`-able macOS window app wrapping
  `ReadingRigUI`'s screens. Exists purely so the screens are clickable
  without a real Xcode app target. Superseded by one once it exists.
- **`Tests/ReadingRigKitTests`** — currently just `BearerAuthMiddlewareTests`.

## Auth

There is no in-app sign-in flow, and building one is a real design
decision that hasn't been made (see `AuthSession.swift`'s doc comment) —
bridging the server's magic-link email flow into a mobile app means a
deep link or universal link, which is out of scope until someone decides
to do it. Today:

```
npm run api-token create <email> [label]   # from the repo root
```

prints a raw Bearer token once (only the sha256 hash is ever stored —
`app/auth/apiToken.server.ts`). Paste it into `SignInView`, which persists
it to the Keychain via `AuthSession`. For fast local iteration,
`SignInView` also prefills its fields from `READING_RIG_API_TOKEN` /
`READING_RIG_BASE_URL` (default `http://localhost:3000`) if set in the
environment `swift run` was launched from — convenience only, the value
that actually gets used always comes from what's in the Keychain.

## What this touches in the main app

- **`openapi/api-v1.json`** (generated by `app/domain/api/openapi.server.ts`,
  written by `npm run generate:openapi`) — the contract this whole client
  is generated from. If a route's zod schema changes shape, regenerate
  this file before `swift build` picks up the change; nothing does that
  automatically.
- **`app/domain/api/openapi.server.ts`** — mostly inlines every schema at
  its call site (see its own doc comment for why), with one deliberate
  exception: `postReadAction`'s four request variants
  (`READ_ACTION_SCHEMAS`) are registered as named `components.schemas` and
  `$ref`'d from a `oneOf`, specifically because
  `swift-openapi-generator` can only turn a `oneOf` into a tagged Swift
  enum when its members are `$ref`s — an inlined one gets silently
  skipped. If a future route needs the same treatment, follow that
  pattern rather than reaching for zod's full `$ref`-registry mechanism
  (still deliberately unused for everything else).
- **`app/auth/apiToken.server.ts`** / **`scripts/apiToken.ts`** — Bearer
  token minting, the CLI from Auth above.
- **`app/analytics.server.ts`**'s `analyticsClientFor(request)` — tags
  every analytics event with `client: "web" | "mobile-app-ios" | "cli"`,
  derived from whether the request carried a Bearer token. This reads
  "Bearer" as "the iOS app" categorically, since it's the only Bearer
  consumer that exists — a second one (Android, a CLI) would need this
  taught to actually tell them apart.
- **`.github/workflows/ios.yml`** — `swift test` on `macos-latest`,
  path-filtered to `ios/**` and `openapi/**` so it stays out of unrelated
  PRs' way. Independent of any contributor's local Xcode install.

## Known gaps / deliberate simplifications

- **No real app target.** Nothing installable on a device or simulator
  yet. The anticipated next step is [XcodeGen](https://github.com/yonaskolb/XcodeGen)
  with a checked-in `project.yml` (not a raw `.xcodeproj` — those produce
  unreviewable diffs) generating a thin app shell that imports
  `ReadingRigUI`. TestFlight/App Store distribution hasn't been designed
  at all; see chat history for a walkthrough of what that would involve
  (Apple Developer Program, App Store Connect app record, Fastlane vs.
  Xcode Cloud) — none of it exists in this repo yet.
- **Whole-paragraph highlighting only**, not an arbitrary text-range
  selection — SwiftUI's `Text` has no selection-range API to build a drag
  gesture on. The server's `spans` shape already supports partial ranges
  (see `HighlightSpanInput`), so this is a client-side gap, not a backend
  one, when someone builds the real gesture.
- **No optimistic UI.** Every write (`highlightWholeParagraph`, `postNote`
  in `WorkReadView.swift`) triggers a full reload of the read view rather
  than patching local state — simpler and correct, at the cost of a
  visible round-trip. The web app has optimistic saves (PR #182); this
  doesn't yet.
- **`multipart/form-data` isn't supported for `postReadAction`'s request
  body** — a narrower `swift-openapi-generator` limitation than the one
  fixed for `application/x-www-form-urlencoded` (see `ReadActions.swift`'s
  doc comment). Irrelevant today since this client never sends multipart
  and the route never receives a file upload.
- **No Rig session chat.** `GET /api/v1/rig-sessions/:workId` (a session
  list) may or may not be wired up yet depending on how far the PR stack
  this file was added in got — check `ReadingRigUI` for a
  `RigSessionsView` or similar. The actual live chat is SSE-based
  (`/api/v1/rig/*`), deliberately excluded from the JSON smoke-test
  surface on the server side, and streaming chat in Swift is a real
  undertaking (SSE parsing, message/tool-call state) that hasn't been
  attempted.
- **No dark mode, no bundled Fraunces typeface.** `RigTheme.readingFont`
  uses the system serif design as a stand-in for Fraunces — organic.css's
  copy is subsetted per-build by `scripts/instanceFraunces.ts`, which has
  no iOS equivalent.

## Local dev loop

```
npm run dev                                          # repo root, in another shell
npm run api-token create <email> "iOS dev client"    # repo root, once
cd ios
swift run ReadingRigDevApp                            # opens a real window
```

`swift build` / `swift test` work the same way any other SwiftPM package
does — no Xcode required for building or testing the library targets, only
for whatever comes after there's a real app target.
